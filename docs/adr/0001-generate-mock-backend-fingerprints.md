# 1. Generate the mock backend's fingerprints from the Nuclei templates

- Status: Accepted
- Date: 2026-08-16

## Context

Seaweed measures how many CVE payloads the WAF blocks. That measurement is only valid for
payloads Nuclei actually puts on the wire.

114 of the 2395 templates in `http/cves` declare a `flow` gate:

```yaml
flow: http(1) && http(2)

http:
  - raw:
      - |
        GET /wp-content/plugins/navis-documentcloud/readme.txt HTTP/1.1
        Host: {{Hostname}}
    matchers:
      - type: word
        internal: true
        words: ['Navis', 'Tags:']
        condition: and

  - method: GET            # the actual payload, only sent if step 1 matched
    path:
      - "{{BaseURL}}/wp-content/plugins/navis-documentcloud/js/window.php?wpbase=..."
```

Step 2 carries the attack. It is only sent when step 1 recognises the application.

The backend was `svenstaro/dummyhttp`, which replies with one fixed body and status code
for every path. No fingerprint ever matched. Measured against the archived run in
`output/`:

- 101 of the 114 flow-gated templates stopped at the detection step.
- 1 reached its payload step.
- 100 of the 101 were reported as `not blocked`, blaming CRS for payloads that were never
  sent.

The same gate mechanism is used more widely: 302 templates carry `internal: true`
matchers and 262 use extractors.

## Decision

Replace dummyhttp with an nginx container that answers `200 text/html` on every path with
a generated page containing every fingerprint the flow-gated templates look for.

The page is generated, not written by hand. `seaweed gen-mock` walks the templates,
collects the `words` of every `internal: true` word matcher in a template that declares a
`flow`, and writes them into `mock/fingerprints.html`. Currently 109 strings, 3.4 KB. The
generated file is committed so that `docker compose up` needs no toolchain; regenerate it
when the templates change.

The page also carries the marker `seaweed-mock-ok`, which the healthcheck in
[ADR 2](0002-single-compose-environment-with-readiness-gate.md) uses to prove that a
request reaches the backend and comes back.

## Consequences

Measured by re-running the 114 flow-gated templates against the pinned CRS image, before
and after:

| backend | reached the payload step | payloads CRS blocked |
| --- | --- | --- |
| dummyhttp | 1 / 114 | ~0 |
| generated fingerprint page | 91 / 114 | 93 |

93 WAF decisions per run that the report previously could not contain.

- Nuclei will report matches that are not real vulnerabilities, because the mock echoes
  fingerprints for software it is not running. Seaweed does not consume Nuclei's findings;
  it counts blocked and unblocked requests from the trace files. The findings output is
  noise and is ignored.
- 23 of the 114 gates are still unmet: 9 use `dsl` matchers and 1 expects its word in a
  response header rather than the body. Both are out of reach of a single static page.
- `mock/fingerprints.html` goes stale when the templates change. It is regenerated by
  hand today; the templates themselves are not pinned yet, so a drift check needs template
  pinning first.
- The mock does not reflect the request back, so templates whose detection depends on
  seeing their own input returned still stop at the gate.

## Alternatives considered

- **Strip `flow:` from the templates before the run** (`yq 'del(.flow)'`), forcing every
  step to be sent. Simpler, and only 5 of the 114 use extractors, so variable chaining
  would break for 5 templates. Rejected as the default because it means running modified,
  unsigned copies of upstream templates. Worth adding later as an explicit mode.
- **A per-template routing table** mapping each fingerprint path to its own response.
  More faithful, but 114 routes to generate and maintain for the same result a single
  page already achieves for 91 of them.
- **Real vulnerable applications** (WordPress, Jenkins, Confluence containers). The most
  faithful option and the heaviest: a handful of apps would cover a handful of CVEs, out
  of thousands.
- **A reflecting echo backend.** Attractive, but it does not help here: the gate words are
  things like `Navis` and `/wp-content/plugins/heat-trackr/`, which do not appear in the
  detection request. Verified against the two examples above.
