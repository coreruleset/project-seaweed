# 15. Generate the mock page at scan time instead of committing it

Date: 2026-08-18

## Status

Accepted. Supersedes the drift check in [ADR 1](0001-generate-mock-backend-fingerprints.md)
and the CI check added in [ADR 5](0005-pin-the-templates-and-collect-the-waf-logs.md).

## Context

`mock/fingerprints.html` is generated by `seaweed gen-mock` from the templates that
`scripts/fetch-templates.sh` pins. It was committed, and CI failed when it differed from
what the pinned templates produced.

That check worked, but it made the templates the only dependency in the repository that
could not be updated automatically. Renovate opens a pull request changing one line in
`scripts/fetch-templates.sh`; CI then fails, because the 881-line generated page in the
same repository no longer matches. Every template bump needed a human to run two commands
and add a commit. The templates are the input that decides every number this project
publishes, and they were the one input with a manual step in the way.

The mechanical fix — have Renovate run `gen-mock` after the update — is not available.
Renovate here is the hosted `app/renovate`, and `postUpgradeTasks` requires its commands to
be allow-listed in `allowedCommands`, which only a self-hosted administrator can set. The
runner image has no Go toolchain either.

The deeper oddity is that the page was committed at all. It is derived data: one command,
from one pinned version, of an input that is itself gitignored. `nuclei-templates/` is not
in the repository. Neither is `crs-tests/`. The page was.

## Decision

Do not commit the page. `.gitignore` it, and generate it in the workflow that needs it,
immediately after fetching the templates it is built from.

CI keeps running `gen-mock`, but no longer diffs the result. What it now checks is that
generation still works, and `gen-mock` grew a floor to make that check mean something: it
fails below 500 fingerprints, against 870 today.

The floor is the part that matters. Staleness was never the dangerous failure — a stale
page is a page built from a known older version. The dangerous failure is a template
format change the harvester silently stops matching: the page comes out short, every flow
gate it should have satisfied fails, and the scan reports those CVEs as never exercised
without erroring anywhere. That is the state this project began in, at 1 exercised CVE out
of 114, and a diff against a committed file would not have caught it — the committed file
would have been regenerated short too, and the diff would have passed.

The compose file now mounts `./mock` as a directory rather than the single file. A
single-file bind mount whose source is absent makes Docker create a directory at that path,
which then breaks `gen-mock` itself on the next run. Mounting the directory turns a missing
page into a 404, which fails the mock's healthcheck and stops the run with the readiness
gate from [ADR 2](0002-single-compose-environment-with-readiness-gate.md).

## Consequences

- A template bump is one line, and Renovate can merge it alone. The page is rebuilt from
  the new version by the run that uses it, so the two cannot disagree.
- `docker compose up` on a fresh clone needs `go run . gen-mock` first. It fails loudly if
  you forget: the mock never reports healthy and nothing else starts.
- The page's contents no longer appear in review. 881 generated lines were never read in a
  diff, and what would be worth seeing — that a gate stopped being satisfied — is visible
  in the report's unexercised count, not in the HTML.
- Two things now have to be true for the mock to be right, and only one is checked here:
  generation works (the floor), and the fingerprints are the ones the templates want (the
  exercised count in the weekly report). The second is the real measurement and always was.

## Alternatives considered

- **A workflow that regenerates the page and pushes to Renovate's branch.** Works with the
  hosted app, since Renovate's branches are in the repository and `GITHUB_TOKEN` can write
  to them. Rejected: it needs `contents: write` on a workflow triggered by bot branches to
  keep committing a file nothing needs committed. Pushing with `GITHUB_TOKEN` also does not
  retrigger checks, so the failed staleness check would stay red.
- **Self-host Renovate to get `postUpgradeTasks`.** A CI runner, a token, and a schedule to
  maintain across the organisation, to automate a command that does not need to exist.
- **Keep the check and accept the manual step.** It is two commands. It is also the reason
  the WAF image sat 27 releases behind: anything with a manual step in front of it stops
  happening, and nobody notices, because the numbers still look like numbers.
